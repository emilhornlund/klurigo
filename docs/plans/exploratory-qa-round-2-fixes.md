## Independently implementable tasks

### QA-014 — Keep protected destination during successful token refresh

- **Journal evidence:** QA-014, `docs/qa/exploratory-testing-round-2.md`, lines 95–138. On Results reload with expired User access and valid refresh, refresh and profile requests return 200, but route redirects home before requesting Results; reopening the route works.
- **Root cause / confidence:** High. `src/components/ProtectedRoute/ProtectedRoute.tsx` evaluates `isUserAuthenticated` immediately and redirects on false. `src/context/auth/AuthContextProvider.tsx` derives that flag solely from access-token validity and starts refresh asynchronously in an effect; there is no pending/recovering signal for protected routes. `src/pages/GameResultsPage/GameResultsPage.tsx` only navigates back after its data query errors, which is not the observed redirect because the query never runs.
- **Implementation scope:** Add the smallest per-scope auth-recovery state needed for route guards to defer redirect while a stored, potentially refreshable session is being checked/refreshed. Use it only to delay the existing guard decision; after successful refresh, admit the original requested route and let its normal query run. If refresh is definitively rejected or no valid refresh token exists, retain existing auth clearing and redirect behavior. Preserve transient-failure retry/recovery semantics and avoid an indefinite blocking state: define how the guard behaves after a transient failure while the provider schedules its existing retry. Do not redirect to home and then reconstruct the route, and do not change Results API behavior.
- **Regression tests:** Extend `src/context/auth/AuthContextProvider.test.tsx` to cover expired access + valid refresh signaling recovery, successful refresh updating state, definitive refresh failure clearing state, and transient failure/retry behavior as currently designed. Extend `src/components/ProtectedRoute/ProtectedRoute.test.tsx` to prove the protected child is not replaced with `<Navigate>` while User recovery is pending, is rendered after success, and redirects after recovery failure. Extend `src/pages/GameResultsPage/GameResultsPage.test.tsx` only if needed for route/query sequencing; preferably add an integration-style router/provider test at the existing route test target if its current mocks cannot represent the race. Keep existing ordinary unauthenticated and Game-scope guard cases.
- **Browser/E2E:** With a synthetic completed game and local authenticated account, alter only that synthetic browser's stored User access expiry to the past, retain its valid refresh credential, and reload `/game/results/:gameID` (actual route pattern per router). Verify local refresh and profile lookup succeed, the Results request follows, and Summary plus tabs render without visiting `/`. Also exercise a protected non-Results route, ordinary valid-token navigation, and invalid/expired refresh recovery to the public route. Repeat a Results tab click/reload around expiry if feasible. No external auth provider or real credentials/tokens.
- **Acceptance criteria:** A refreshable User session retains its requested protected URL and renders it after refresh; protected routes still reject absent/invalid sessions; successful refresh and profile hydration are unchanged; definitive invalid refresh still clears auth and recovers publicly; transient refresh behavior neither traps users indefinitely nor causes premature redirect while recovery is active.
- **Risks / constraints:** Auth context is shared by all protected routes, so pending-state semantics must distinguish “refresh in progress” from “session is authenticated” and be scoped correctly. Avoid flicker/redirect loops, races between the provider effect and guard, stale pending state after logout/token replacement, and accidental changes to guest-only or Game-scope guards. Do not merge QA-016's request policy into this fix.
- **Verification commands:** `yarn workspace @klurigo/klurigo-web test:unit -- src/context/auth/AuthContextProvider.test.tsx src/components/ProtectedRoute/ProtectedRoute.test.tsx src/pages/GameResultsPage/GameResultsPage.test.tsx`; `yarn workspace @klurigo/klurigo-web typecheck`; browser verification per `docs/development/browser-verification.md`; applicable synthetic Results E2E only after test DB/Redis isolation is verified.

### QA-016 — Recover host authentication without creating another game

- **Journal evidence:** QA-016, `docs/qa/exploratory-testing-round-2.md`, lines 228–279. The first host attempt creates a game (201), then `/auth/game` returns 401 because User access expired and the auth request disables refresh. Immediate retry succeeds after refresh but creates another game.
- **Root cause / confidence:** High. `src/pages/QuizDetailsPage/QuizDetailsPage.tsx` creates a game before authenticating it. `src/api/resources/auth.resource.ts` explicitly passes `{ refresh: false }` to `/auth/game` whenever a User access token is present, so the shared API client cannot refresh/retry the User credential on this authenticated-host path. The generic catch maps failure to invalid game code. `createGame` is therefore across the irreversible boundary when authentication fails; simply enabling a blind whole-flow retry would duplicate game records.
- **Implementation scope:** At the auth-resource/API-client boundary, allow the existing User-scope refresh-and-retry behavior for the single `/auth/game` request when a User token is the credential, preserving the existing Game-scope behavior for anonymous/game-token re-authentication. The API core defaults `refresh` to true, refreshes the selected scope, then replays that request once with the refreshed token; `auth.resource.ts` currently disables this by passing `{ refresh: false }` for the User-auth case. Reuse the already-created `gameId` for the retried auth request; never repeat `createGame` as part of token refresh/retry. Handle a definitive failure after creation as a recoverable host-auth failure that leaves the user able to retry authentication for that same created game where the existing flow permits it, or otherwise prevents a second game creation on retry; choose the narrowest correct recovery after tracing server lifecycle and client state. Ensure actual invalid game-code failures retain their existing fallback, while a failed User-token refresh is not presented as an invalid game code. Avoid hiding the failure behind only a new message. Keep auth/game API contracts unchanged unless code inspection proves that client-side recovery cannot be achieved with the current contract.
- **Regression tests:** Extend `src/api/resources/auth.resource.test.ts` for authenticated User-token `/auth/game` request options and preserve the existing anonymous Game-token `{ scope: TokenScope.Game }` case. Add/extend `src/api/api-client-core.test.ts` to verify an expired User token refreshes and retries the same `/auth/game` request exactly once (and no duplicate retry/refresh), including refresh rejection. Extend `src/pages/QuizDetailsPage/QuizDetailsPage.test.tsx` to assert create called once, auth retried against the same created game identifier, navigation only after auth succeeds, and a failed auth/recovery followed by user retry does not create another game. If the host UI needs to retain the created game ID or expose retry semantics, add focused component/page test coverage at `src/pages/QuizDetailsPage/components/QuizDetailsPageUI/QuizDetailsPageUI.test.tsx` and keep this state scoped to the current host attempt.
- **Browser/E2E:** With an owned synthetic quiz, expire only its local User access credential while retaining valid refresh; confirm Host Game once. Observe successful local refresh and authenticated host lobby with exactly one game creation request (one `/api/quizzes/:quizId/games` 201) and one successful logical game-auth operation against that returned game ID (a network retry after refresh is acceptable, but no second creation). Also force refresh/auth failure using synthetic local credentials: verify the failure is not mislabeled as a code mismatch, host can recover/retry the same created game or the UI prevents an unnecessary second creation, then verify success. Inspect local game state only through supported local app/API/test surfaces; never inspect or mutate imported records.
- **Acceptance criteria:** Expired User access with valid refresh can host with one game creation and successful game authentication; refresh retry reuses the same `gameId`; a failed host-auth attempt cannot cause a needless additional game on retry; anonymous game authentication still uses Game-scope credentials; genuine invalid game-code handling remains correct for join/auth cases; no backend/API contract change without demonstrated necessity.
- **Risks / constraints:** The two-request flow has a side-effect boundary at creation. Do not retry the entire create-then-auth chain, create a compensating/deletion API, or treat every 401 as an invalid code. Confirm current `api-client-core` retry/coalescing behavior, selected token scope, server idempotency/lifecycle, and what state survives a failed authentication before implementing recovery. Keep this task independent of QA-014 despite shared refresh machinery.
- **Verification commands:** `yarn workspace @klurigo/klurigo-web test:unit -- src/api/resources/auth.resource.test.ts src/api/api-client-core.test.ts src/pages/QuizDetailsPage/QuizDetailsPage.test.tsx src/pages/QuizDetailsPage/components/QuizDetailsPageUI/QuizDetailsPageUI.test.tsx`; `yarn workspace @klurigo/klurigo-web typecheck`; synthetic local browser host-flow verification; applicable E2E only with verified isolated test MongoDB and Redis DB 1.

### QA-015 — Make Pin coordinate selection keyboard-operable

- **Journal evidence:** QA-015, `docs/qa/exploratory-testing-round-2.md`, lines 140–178. The live accessibility tree exposes prompt and submit, but not the Pin image/target; pointer handlers work in source while keyboard users cannot move the default center pin.
- **Root cause / confidence:** High. `src/components/PinImage/PinImage.tsx` renders the interactive overlay as a non-focusable `div` with pointer-only handlers. `src/states/common/QuestionAnswerPicker/components/AnswerPin/AnswerPin.tsx` passes the selected `position` and `onChange`, but no accessible alternative or position announcement. This is an operation and feedback gap, not only a missing name.
- **Implementation scope:** Give the interactive Pin target an appropriate accessible semantic and focus behavior (for example, a named focusable group/control, chosen based on how coordinate manipulation is represented), and implement documented keyboard coordinate selection/movement using normalized 0–1 coordinates clamped to the image. Arrow keys must adjust the pin in a predictable direction; define a practical increment and optional larger-step modifier if helpful, while ensuring endpoints are reachable. Keep the initial center and existing pointer drag behavior. Provide accessible feedback that announces the chosen position, preferably a concise live status with rounded percentage coordinates, without changing the visual interface. Disabled/non-interactive and submitted states must not remain keyboard-operable. Keep generic `PinImage` compatibility for non-answer uses; scope interaction semantics or label props as necessary rather than adding irrelevant labels to decorative/disabled instances.
- **Regression tests:** Extend `src/components/PinImage/PinImage.test.tsx` for focusability/accessible naming where enabled, arrow-key movement and clamping, emitted `onChange`/`onValid(true)`, disabled state, and preserved pointer drag. Extend `src/states/common/QuestionAnswerPicker/components/AnswerPin/AnswerPin.test.tsx` for the live answer's accessible name/position feedback and keyboard-selected coordinates submitted through `onSubmit`; verify feedback follows position changes and keyboard input does not submit accidentally. Use role/name assertions rather than snapshot-only coverage.
- **Browser/E2E:** Join a synthetic local Pin game on desktop and narrow/mobile viewport. Tab to the image coordinate control, use arrows to move to visibly distinct non-center positions including an edge, and verify the announced position tracks the pin. Submit and verify player answer, result, and host response/scoring reflect the chosen coordinate. Confirm pointer drag and touch/pointer placement still work and the image/pin visual appearance is unchanged. After answer submission or when non-interactive, verify control cannot be moved.
- **Acceptance criteria:** Keyboard-only player can focus, place, and adjust a Pin answer over the full image area; assistive technology receives a meaningful control name and updates indicating selected position; coordinate payload equals displayed position; pointer/touch placement, submission/scoring, and existing Pin visuals remain intact; disabled states prevent coordinate changes.
- **Risks / constraints:** Do not make the image itself a misleading button if its interaction is continuous coordinate selection; choose semantics and keyboard instructions suitable for screen readers. Ensure focus is visible within existing styles without redesigning the interface. Avoid key handling that steals arrow keys from surrounding controls or causes page scrolling while the Pin control is focused. Percent feedback should be human-readable without quantizing submitted coordinates.
- **Verification commands:** `yarn workspace @klurigo/klurigo-web test:unit -- src/components/PinImage/PinImage.test.tsx src/states/common/QuestionAnswerPicker/components/AnswerPin/AnswerPin.test.tsx`; `yarn workspace @klurigo/klurigo-web typecheck`; browser keyboard/accessibility and visual verification at desktop and mobile; isolated synthetic game E2E if required and safe.

### QA-017 — Keep Range input, slider, and submitted answer aligned

- **Journal evidence:** QA-017, `docs/qa/exploratory-testing-round-2.md`, lines 228–309. On a 10–90 question with slider `step=2`, entering 67 leaves the number field at 67 while the browser's range control exposes 68; submission uses numeric state.
- **Root cause / confidence:** High. `src/states/common/QuestionAnswerPicker/components/AnswerRange/AnswerRange.tsx` binds the range control to the question-provided `step`, but the numeric field and `value` state accept any integer in bounds. `src/pages/QuizCreatorPage/components/QuizCreatorPageUI/components/QuizPreview/quiz-preview-question.ts` uses shared `calculateRangeStep(min,max)` to produce coarse steps for Classic ranges; that policy is used to create the UI's slider step, not to define integer answer/scoring rules. The live handler parses the slider value as an integer and submission sends state.
- **Implementation scope:** Audit all callers of `AnswerRange`, the shared `calculateRangeStep` use, and backend Range validation/scoring to establish that any integer in `[min,max]` remains valid and scores using the submitted number. If confirmed, set the live response slider to step 1 (or the smallest compatible integer step) while retaining the question's `step` type/prop for other consumers as needed; this avoids lossy HTML range sanitization and does not change answer or scoring rules. If integer answer rules cannot support step 1 in some mode, define an explicit consistent constrained-entry policy before coding, but do not silently round: the number control must communicate/enforce exactly the same allowed set as the slider. Ensure both input events update the same answer state and validity, and that answer submission reflects the exact shared value. Do not change `calculateRangeStep` or scoring unless investigation demonstrates they encode intended answer restrictions.
- **Regression tests:** Extend `src/states/common/QuestionAnswerPicker/components/AnswerRange/AnswerRange.test.tsx` with the reported `min=10,max=90,step=2,value=67` case: numeric and slider values both remain 67 and submit sends exactly 67; cover off-step values at both bounds/interior, slider-to-input and input-to-slider synchronization, and no rounding. Keep the prop-driven step test only if the implementation continues to use the prop; otherwise assert the response slider's effective integer step and preserve existing preview/editor step coverage in `src/pages/QuizCreatorPage/components/QuizCreatorPageUI/components/QuizPreview/quiz-preview-question.test.ts`.
- **Browser/E2E:** In a synthetic Classic Range game configured to produce coarse step 2, type 67, compare the spinbutton value, slider DOM value/thumb, accessible values, and submitted payload before sending. Verify all show/submit 67, score matches existing Range margin rules, and adjacent integer values can be selected from either control. Check min/max and an on-step value. Run any added gameplay E2E only against verified isolated test stores; no imported quiz/game data.
- **Acceptance criteria:** Numeric field, slider value/thumb, accessible value, and submitted answer always represent the same integer; 67 remains 67 and is never rounded/silently changed; both controls can select every currently valid integer if that is the demonstrated product/scoring contract; existing integer answer validation, scoring, bounds, and editor/preview coarse-step policy are unchanged.
- **Risks / constraints:** The coarse generated step may have been intended as a gameplay constraint despite scoring accepting arbitrary integers; verify backend scoring and UX intent before settling on step 1. Avoid modifying shared range calculation or score tolerance as a convenience. Test native range sanitization in a real browser as unit DOM emulation may not reproduce it fully.
- **Verification commands:** `yarn workspace @klurigo/klurigo-web test:unit -- src/states/common/QuestionAnswerPicker/components/AnswerRange/AnswerRange.test.tsx src/pages/QuizCreatorPage/components/QuizCreatorPageUI/components/QuizPreview/quiz-preview-question.test.ts`; `yarn workspace @klurigo/klurigo-web typecheck`; browser verification with off-step entry and slider interaction; synthetic gameplay E2E only after test DB/Redis isolation is verified.
